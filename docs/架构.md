# 架构

> 从数据流讲起，不从"装了哪些插件"讲起。

## 一、一条消息的完整过程

### 你 → 她

1. **NapCat** 收到 QQ 消息，写进队列
2. **qq-bridge** 轮询 `get_msg`（默认几秒一次）
3. 判断：私聊 / 群聊 / 有没有 @；再和**水位文件**比对，比上次读到的位置新才处理
4. 新消息 → `agent.followup()` 塞进目标会话
5. DSH 起一轮：记忆注入 → 生成回复 → 回复后心情判定
6. **qq-bridge** 监听 `turn/end`，把回复取出来 → `send_private_msg` → NapCat → 你的 QQ

### 她 → 你（主动）

1. **speak-up** 定时器每 N 分钟响一次
2. 硬闸门：总开关 → 安静时段 → 目标会话活着且空闲 → 搭话冷却
3. 挑**目的**（本仓库补丁的功能）：
   - 真发时：最近若干条对话交给模型，让它想一句短由头
   - 失败 / 演练：从内置词库挑（关心 / 分享 / 好奇 / 续聊），最近几条不重复
4. **掷骰**：掷 0~100，小于命中线才开口
   - 命中线 = 峰/谷基础值 × 时机因子 + 没中加成
5. 掷中 → 拼一段话（明确告诉模型"这是你自己冒出来的念头"）→ `followup()`
6. 她回一轮 → qq-bridge 发到 QQ

**为什么必须用 `followup()` 而不是直接写消息**：只有 followup 才会让 DSH 认领成一轮真实回合，
直接 append `user/message` 事件等于伪造历史，会被校验拦下或让模型看不见。

### 心情

每轮结束后调一次模型判断"这轮心情怎么变了"（只输出 JSON），变化量按比例吸收。
结果注入下一轮 system prompt，并可投到桌面挂件。

### 记忆

聊天记录按时间切片，超过容量就压缩（旧内容变模糊），召回时按相关度取、带时间标记。

## 二、五个组件

| 组件 | 管什么 | 关掉会怎样 |
|---|---|---|
| `dsh-qq-bridge` | QQ ↔ DSH 双向通道 | 收不到也发不出 |
| `dsh-speak-up` | 自己找话头 | 只在被叫时说话 |
| `dsh-feiyu-mood` | 心情 | 语气回到中性 |
| `dsh-fish-memory` | 会淡忘的长期记忆 | 越聊越只剩最近的上下文 |
| `dsh-group-chat` | 本地多角色群聊（实验） | 只有你和她 |

全部 MIT，都建议用 `link:` 安装（代码留在自己的目录里，改完重新装卸即可生效）。

## 三、后端

| 东西 | 默认端口 | 说明 |
|---|---|---|
| OneBot HTTP | 3000 | 插件走这个收发 |
| WebUI | 6099 | 扫码登录 / 看状态 |

### 看门狗的三档逻辑

| 探测 | 含义 | 动作 |
|---|---|---|
| OneBot 通 | 健康 | 什么都不做 |
| 两个都不通 | 进程没了 | 直接拉起 |
| OneBot 不通、WebUI 通 | **进程在但登录掉了** | 等够 15 分钟重启一次试快速登录 |

第三档的退避：**15 → 30 → 60 分钟**，连续 3 次还登不上就停手。

**为什么要退避**：重启会把正在显示、可能已经准备扫的二维码作废。每 5 分钟重启一次 = 用户永远扫不上。

## 四、目录与文件

| 位置 | 内容 |
|---|---|
| NapCat 安装目录 | 运行时、`napcat-pw.txt`、日志、`watchdog-state.json` |
| `~/.dsh/qq-bridge-config.json` | 桥的配置 |
| `~/.dsh/speak-up-config.json` | 主动搭话配置 |
| `~/.dsh/group-chat.json` | 群聊成员与上限 |
| `~/.dsh/<插件名>/` | 各插件的运行时数据 |

> 具体路径随插件版本会变，以各插件 README 为准。

---

## 五、设计取舍

- **每个环节都能单独关**：出问题能二分定位，而不是"一挂全挂"。
- **不依赖云服务**：除了模型 API，全在本机。
- **代价**：四五个进程 + 两个计划任务，任何一环掉链子都得自己查。
