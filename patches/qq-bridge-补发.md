# qq-bridge 补发：离线消息不丢

> ⚠️ **这不是可直接 `git apply` 的 diff。**
> 本机的 `dsh-qq-bridge` 是 0.3.6，而上游已经改名 `dsh-qq-link` 并到 1.5.x，
> 结构差得太多，硬凑 diff 只会害人。这里是**设计 + 关键代码**，照着改或提 PR 都行。

## 要解决的问题

原来的行为：桥重启后，"上次收到消息的时间"是从内存初始化的（= 此刻）。
**关机期间她发的话，醒来就被跳过了**——永久丢失，用户完全不知道。

## 三处改动

### 1. 水位落盘

内存里那个"上次时间"改成写文件：

```js
const 水位文件 = join(目录, 'qq-bridge-watermark.json')

function 读水位() {
  try {
    const j = JSON.parse(readFileSync(水位文件, 'utf8'))
    return j && typeof j === 'object' && !Array.isArray(j) ? j : {}
  } catch { return {} }
}

function 写水位(私聊, 群) {
  try {
    mkdirSync(目录, { recursive: true })
    writeFileSync(水位文件,
      JSON.stringify({ 私聊: Number(私聊) || 0, 群: Number(群) || 0, t: Date.now() }), 'utf8')
    return true
  } catch { return false }
}
```

**关键**：写水位不要每轮都写（4 秒一次太频繁），限流到 30 秒一次。

### 2. 一批消息过一遍，而不是来一条转一条

```js
const 收一批 = async (列表, 起, 种类) => {
  const 挑 = []
  for (const 条 of 列表.slice().sort((a, b) => (a.time || 0) - (b.time || 0))) {
    if (Number(条.user_id) !== 她的号) continue   // 只认她（群聊也只认她）
    if ((条.time || 0) <= 起) continue            // 上次已经看到这儿了
    if (已转消息.has(条.message_id)) continue     // 去重
    const { 文字, 图们 } = 条转片段(条)
    if (!文字 && !图们.length) { 已转消息.add(条.message_id); continue }
    挑.push({ 条, 文字, 图们 })
  }

  // 两道闸：条数上限 + 时间上限
  const 截 = 挑.length > 上限 ? 挑.slice(挑.length - 上限) : 挑
  ...
}
```

`上限` 和 `最久小时` 来自配置（默认 20 条 / 72 小时），**超出只补最近的**。

### 3. 送不进去就不推进水位（最重要的一条）

```js
const 结果 = await 转入一条(x.文字, x.图们, x.条.message_id, 延迟秒)
if (!结果 || 结果.ok !== true) {
  // 没送进去就别推进水位 —— 留着，等目标会话回来再补，
  // 不然这条就被永久吞掉了（以前就是这样：水位先走，消息没了）
  记账(`这条先没送进去（${缘由}），水位停在这儿，下一轮再试`)
  break
}
```

配套的还有：**失败日志限流**（同一原因 60 秒内只记一次），
不然目标会话没开的那几个小时里，日志会被刷爆。

### 4. 补发的消息要带时间说明

补进去的消息不是"刚刚说的"，模型不知道就会当成当前的对话：

```
（这条是 12 分钟前发的，你那会儿不在线，现在补给你）原文……
```

延迟 < 120 秒的不加这句（补得够快，不算"迟到"）。

## 自测

本机有配套测试（未开源，说明思路）：

| 测试 | 断言数 | 覆盖 |
|---|---|---|
| `补发.mjs` | 10 | 水位读写、上限截断、去重、时间说明 |
| `补发-目标没活着.mjs` | 7 | 目标会话不可用时**水位不推进**、日志限流 |

核心断言就一句：**失败之后，再读水位必须还是旧值。**

## 怎么用

1. 看看上游 `dsh-qq-link` 是不是已经有等价功能（它在 1.x 里改了很多）
2. 没有的话，按上面三块改，或者把这个文档当 PR 描述
3. 改完务必测「目标会话不存在时会不会吞消息」——这是最容易写错的地方
